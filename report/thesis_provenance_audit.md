# Thesis provenance and technical audit

Audit date: 2026-09-22

## 1. Executive conclusion

The supplied thesis is clearly a conceptual predecessor to `main.tex`, not an unrelated document. Both studies concern prediction-informed last-mile delivery intervention, use the Xe dù Ho Chi Minh City delivery dataset, and discuss nearest-neighbor and Clarke--Wright routing. The new manuscript, however, replaces the thesis's route-level delay-count regression and assumed intervention success with a substantially different framework: customer-level lateness probabilities, actionability, an intervention budget, selective forward relocation, a cumulative distance constraint, and full counterfactual schedule propagation.

The most accurate description is therefore **an extension and methodological redesign inspired by the supplied thesis**. It should not be presented as wholly independent. The thesis should be acknowledged and cited if it is publicly citable or if the author/advisor permits citation. Its prose, figures, results, and code should not be copied without attribution and permission.

A normalized exact-text scan found no shared 20-word phrase and no shared 10-word phrase other than the common Kaggle dataset URL. This is useful evidence against obvious verbatim reuse in the current `main.tex`, but it is not a formal plagiarism assessment.

The supplied code must not be used as empirical support for the claims planned in `main.tex`. It contains important leakage and evaluation problems, and its reported “customers saved” values are imposed through a fixed success-rate assumption rather than generated by route-time simulation.

## 3. Dataset inspection

The supplied CSV contains 2,403 rows and 18 columns:

```text
id, createdAt, deliveredAt, expectedDeliveryTime, orderCode,
package_name, orderStatus, senderAddress, senderLat, senderLng,
receiverAddress, receiverLat, receiverLng, shippingDistance,
shipper, weight, serviceType, image
```

Important audit results:

- 2,290 rows have both a valid `deliveredAt` and `expectedDeliveryTime`.
- Among those rows, 463 are late under `deliveredAt > expectedDeliveryTime`, a 20.22% late rate.
- The data spans 2023-05-04 through 2024-08-27 when considering the available timestamps.
- There are 17 non-null shipper identifiers.
- All 2,403 records have `orderStatus = success`; this field cannot distinguish successful from failed deliveries in this extract.
- `expectedDeliveryTime` is missing for 4.37% of rows and `deliveredAt` for 0.33%.
- Sender and receiver coordinates are both present. This supports the concern that the source operation may involve pickup-and-delivery orders rather than a pure common-depot delivery route.

These counts reproduce the thesis statement that 2,290 records remain after removing rows missing critical lateness fields.

### Interpretation

The manuscript's novelty is not that prediction and routing are being connected for the first time in this local project; the supplied thesis already did that at a coarse level. The defensible novelty is the stricter and more explicit decision design:

1. moving from daily count regression to customer-level risk;
2. separating risk from actionability;
3. imposing an intervention budget and cumulative routing tolerance;
4. accepting only moves that improve total tardiness;
5. recomputing outcomes for every customer instead of assigning an intervention-success percentage;
6. enforcing an ex-ante information boundary.

The paper should state this distinction clearly when describing its contribution.

## 5. Technical findings in the supplied code

### 5.1 Critical: post-outcome feature leakage

`1. Preprocessing.py` derives `delivery_date`, `hour_of_day`, route order, work end, and actual working hours from `deliveredAt`. `2. Machine Learning.py` then uses `actual_working_hours`, `orders_per_hour`, and `actual_vs_planned_time` as predictors. These values are unavailable before route execution and cannot support ex-ante intervention.

The three-day rolling feature is also leaky:

```python
df_ml.groupby('shipper')['daily_delayed_locations'].transform(
    lambda x: x.rolling(window=3, min_periods=1).mean()
)
```

Because it is not shifted, the rolling mean contains the current row's target. The thesis identifies this feature as the most important predictor, so the reported model performance is not a reliable estimate of ex-ante prediction quality.

### 5.2 Critical: outcome-defined route groups

Daily routes are grouped using the calendar date extracted from `deliveredAt`. This assigns an order to a route using its realized completion date. A valid operational route group should be defined by information known at assignment/dispatch, such as an assignment date, planned service date, or an explicitly justified date derived from `createdAt`.

### 5.3 Critical: actual sequence selects the routing method

For each courier-day, the code generates NN and CWS cluster sequences and then chooses whichever is more similar to the realized cluster sequence. This means the “best route” used downstream depends on post-execution information. It is not an ex-ante baseline route.

This also explains why `main.tex` is correct to require a fixed deterministic primary heuristic and reserve alternatives for robustness analysis.

### 5.4 Critical: ground truth changes the predicted candidate set

`5. Integration.py` reads the actual delayed count before completing candidate selection. Examples include:

```python
if U_predicted == 0 and actual_delayed_count > 0:
    U_predicted = max(1, int(actual_delayed_count * 0.5))
```

and stopping candidate selection using a threshold based on `actual_delayed_count * 0.8`. This leaks the test outcome into the operational decision and inflates detection results.

Similar ground-truth-dependent caps occur in the validation and sensitivity scripts.

### 5.5 Critical: “customers saved” is assumed, not simulated

The integration code calculates:

```python
customers_saved = int(true_positives * integration_rate)
```

with a default `integration_rate = 0.85`. The optimized order is not used to propagate travel and service times, and lateness is not recomputed against expected delivery times. Therefore, the reported reduction from 321 to 274 late deliveries and the 14.6% improvement are consequences of the assumed 85% rate, not demonstrated routing outcomes.

The new paper must not reuse those numbers as evidence for PISR.

### 5.6 Critical: route optimization is disconnected from impact evaluation

The code produces an “optimized” sequence for selected orders, but `calculate_integration_impact` uses only classification true positives and the fixed rate. It never compares the original and modified route distances, arrival times, late counts, or tardiness. Thus the route-reoptimization output has no causal role in the reported impact.

### 5.7 High: pickup-and-delivery feasibility is ignored

The dataset contains a sender and receiver for every order, but routing uses receiver locations only and assumes one approximated depot. If packages are not already consolidated at a depot, resequencing receiver stops without sender stops can violate pickup-before-delivery feasibility.

This issue must be resolved through data documentation, a defensible delivery-only subset, or an extended pickup-and-delivery model.

### 5.8 High: hyperparameter cross-validation is not temporal

Although the final train/test split is chronological, `GridSearchCV(cv=5)` uses ordinary folds inside the training block. Time-ordered tuning should use rolling or expanding-window splits.

The label encoder is also fitted before the split. More importantly, treating arbitrary shipper IDs as ordered numeric values is not an appropriate encoding for tree-independent model comparison.

### 5.9 High: prediction target does not match the new manuscript

The thesis predicts a route-level count of delayed stops. It does not produce calibrated customer-level probabilities. A route count cannot be treated as `p_i`, and the GUI's constructed risk score based on distance to centroid is not a model probability.

### 5.10 High: the CWS implementation is not a standard constrained savings implementation

The supplied merging code joins route lists without checking that the chosen nodes are route endpoints, route orientation, capacity, precedence, or time constraints. It is suitable only as rough prototype code. The PISR project needs a tested, deterministic implementation or should keep Clarke--Wright strictly as a robustness constructor with explicit invariants.

### 5.11 Medium: route-similarity calculation is fragile

Cluster IDs are concatenated into character strings before Levenshtein distance is computed. This works only while cluster identifiers are single digits. Multi-digit identifiers become ambiguous. Sequence distance should operate on tokens, not concatenated characters.

### 5.12 Medium: report and implementation semantics need reconciliation

The report describes a fixed/approximated depot coordinate, while preprocessing recomputes the depot as the mean of all receiver coordinates. The report also discusses predicted delayed locations, but the model predicts a daily count and locates customers later using heuristic rules and realized-data adjustments.

### 5.13 Execution status in the current workspace

All ten scripts parse as valid Python. They do not run end-to-end in the current workspace as supplied:

- `scikit-learn`, `python-Levenshtein`, and `PyQt6` are unavailable;
- the GUI imports module names such as `Preprocessing`, `ML`, `Routing`, and `Intervention`, which do not match the supplied filenames;
- scripts expect generated intermediate CSV files in the current directory;
- there is no environment file, locked dependency list, automated test suite, or run manifest.

Dependencies should not be installed merely to reproduce the old pipeline. The new implementation should use the available environment and independently tested modules described in `design.md`.

## 6. What may be reused

### Reuse as background or requirements input

- Dataset field names and basic cleaning logic.
- The observed lateness definition `deliveredAt > expectedDeliveryTime`.
- The idea of chronological evaluation, after correcting feature and tuning leakage.
- Haversine-distance formulas, independently implemented and tested.
- NN and CWS as classical comparison heuristics, not the supplied daily oracle selection.
- The thesis's limitations and motivation as a rationale for the stricter PISR redesign.

### Do not reuse as empirical evidence

- Reported ML scores until the model is rebuilt without leakage.
- The 47 “customers saved,” 14.6% improvement, or any result derived from the fixed 85% rate.
- Route-similarity-selected baselines.
- At-risk customer lists affected by actual delayed counts.
- The existing optimized sequences as proof of feasibility or lateness improvement.

### Code-reuse rule

No code should be copied into the new system until ownership and reuse permission are confirmed. Even with permission, the safer approach is a clean implementation from the equations and system specification in `main.tex` and `design.md`, accompanied by tests.
